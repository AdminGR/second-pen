# Mobile Companion

Source: [Blueprint](../BRAINSTORMING/Second-Pen-BLUEPRINT.md). Layout is not designed yet. Principles are.

## Purpose

This is the governing surface, not a companion in the "lite" sense. **The primary surface is the phone.** One-handed dictation should start and finish the job: brief → destination → listen → push. Layout is not designed yet; desktop mockups do not make desktop the lead.

Desktop shares the same voice model, session, draft, and push. It is not a separate product with extra capabilities the phone lacks.

## Core Responsibilities

- Dictation as a normal way to start, equal to typing.
- Destination as a parameter, reachable without a desktop-style icon rail.
- Draft as a pinned, reviewable object (read and listen), not a disappearing chat bubble.
- Push as the clear end of the session.

Do not translate desktop rail navigation downward and call it mobile.

## Relationship to Desktop

- Same job, same model, same draft identity.
- Desktop may show more of the draft at once (manuscript-like reading). Mobile must still complete the loop.
- If a feature cannot be done one-handed on the phone, it is not a core feature. It is a corner.

## Offline / Online Behavior

Not designed. Generation, dictation, and playback likely need a connection in the first slice. Offline is not a reason to split the product. If a session cannot generate, the brief and destination should not be lost.

## Open Questions

- Mobile layout for destination, draft, listen, and push without a two-panel desktop skeleton.
- Microphone affordance vs. always-listening expectations (product should not require always-on).
- How Listen works with phone audio (speaker, headphones, interruption).
- Whether quiet seed happens on mobile at all, or only on desktop as a rare setup.
